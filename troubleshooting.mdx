Common errors you might hit, and how to fix them. Each entry states the cause and the fix.

## `update` / `delete` fails on an in-memory connection

These require **durable storage**. Connect with a path or an object-store URI
(`s3://`, `gs://`, `az://`), not `memory://`:

```python
db = infino.connect("./data")   # not "memory://"
```

## `update` reports a cardinality mismatch

`update` replaces matched rows **1:1**, so the number of rows your predicate matches must
equal the number of replacement rows you pass. Match a specific set (e.g. by `doc_id`)
and supply exactly that many rows.

## `update` / `delete` fails with "mutation cap is 100000"

A single `update` or `delete` is refused when its predicate matches more than 100,000
rows; the error reads `predicate matched N rows; mutation cap is 100000`. Narrow the
predicate and run it in several calls, for example one per date range or id range.

## "Table already exists" on `create_table`

The table is already in the catalog. Use `open_table` to get a handle to the existing
table, or `drop_table` first if you mean to recreate it. In Python this is a `ValueError`
whose message names the table.

## "Unknown table" / "not found"

The table name doesn't exist in the catalog (a typo, or it was never created). Check
`list_tables()`. In Python, `open_table` raises a `KeyError`. In SQL, the table name
passed to a search function (`bm25_search('docs', …)`) must be an existing catalog table.

## "no full-text index for column" on a search

`bm25_search`, `token_match` and `exact_match` read the full-text index, so the column
must be one you declared with `IndexSpec.fts(...)`. The message lists the columns that
are indexed. To match on a column without an index, filter it in SQL
(`WHERE doc_id = '42'`).

## Type or vector-dimension mismatch on `append`

A value must fit its column's type: text into an `Int64` column is refused with an
error saying the column is `Int64` but the batch carries `LargeUtf8`. For the vector column, **each
vector's length must equal the index dimension** you declared in
`IndexSpec.vector(column, dim, …)`, and that must match your embedding model's output.

## A misspelled key on `append` creates a new column

When you append rows as records (a list of dicts in Python, an array of objects in
Node.js), a key the table does not have yet is not an error: it adds a column, typed
from its values. A typo such as `yaer` therefore lands in a new `yaer` column instead of
`year`. Check the table's columns if a field reads back as null.

## `append` fails with HTTP 413 on Infino Cloud

The request body went over the hosted data-plane cap of 512 MiB per request. Split the
load into smaller appends; target 100 MiB or less of Arrow data per batch, sized down
if rows carry wide vectors. See [Limits](/cloud/limits).

## `append` fails with HTTP 503 on Infino Cloud

Not a size error and not an outage. The service bounds the total in-flight
request-body bytes across concurrent requests, and sheds rather than queues when
admitting one more would exceed that budget. Honour the `Retry-After` header (one
second) and retry the **same** batch unchanged; the pressure drains as other requests
complete. If it recurs, lower ingest concurrency rather than batch size, since parallel
large appends are what exhaust the budget. See [Limits](/cloud/limits).

## Node.js: integer columns read back as `bigint`

An `int64` column accepts a whole JavaScript `number` on `append` (`2021` works; a
fractional value such as `1.5` is refused). Reads go the other way: `int64` values and
`_id` come back as **`bigint`**, so compare with `2021n` or convert with `Number(x)`
before mixing them with ordinary numbers.

## Rust: "cannot have two global allocators"

Infino installs `mimalloc` by default. If your process already sets a global allocator,
turn Infino's off:

```toml
infino = { version = "0.11", default-features = false }
```

## A vector query in SQL is rejected

`vector_search` / `hybrid_search` expect the query vector as a **comma-separated string
literal** (`'0.12,0.04,...'`) or a **SQL array literal** (`[0.12, 0.04, ...]`), not a
bare column or an unquoted list.

## Deleted rows still show up when reading Parquet directly

A raw Parquet read returns the rows as stored in the superfiles and does **not** apply
tombstones. For the live view (with `update` / `delete` applied), query through Infino
rather than reading the files directly. See [Open format](/guides/parquet-interop).
