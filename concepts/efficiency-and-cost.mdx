Infino is built so a query reads only the data it needs. Your corpus can be large and
mostly cold on object storage, while you pay compute for the queries you actually run
and the working set you keep hot. Cost tracks usage, not the size of the dataset.

## Read only what the query needs

A query goes through three steps before it touches your data, so it rarely downloads
whole files:

1. **Pin a snapshot.** The query starts from a fixed view of the table, so concurrent
   writes can't change its answer mid-flight (see [Snapshots and freshness](/concepts/freshness)).
2. **Prune from the catalog.** Each file carries small summaries in the manifest: value
   ranges, a keyword "is this term present?" filter, and vector centroids. The query
   reads just these summaries to skip files that can't match, before fetching any file
   contents. The same summaries cover scalar, keyword, and vector signals, so a hybrid
   query prunes on all three together.
3. **Fetch only the bytes that survive.** For the files left, Infino pulls just the
   relevant byte ranges, such as a posting list or a handful of vector clusters, not the whole
   file. A keyword filter in SQL is answered from the index and decodes only the matching
   rows, rather than scanning a whole column.

The result is the cost model that matters: **you pay for what you query, not for keeping
everything in memory.**

## Indexes sit with the data

Each [superfile](/how-it-works) is a single Apache Parquet file with its BM25 and vector
indexes built into it. The index and the data it describes live together, so resolving a
match doesn't mean a round trip to a separate index service. Infino reads the index and
the matching rows from the same file.

## A hot working set, a cheap long tail

Object storage is cheap and durable but slower per request, so Infino layers a cache
between compute and storage:

| Tier | Where the data is | Speed |
| --- | --- | --- |
| **Cold** | only on object storage | served from ranged reads while the file fills the local cache in the background |
| **Warm / hot** | resident locally | memory-mapped, at local-disk / RAM speed |

The cache has a size budget and evicts cold files when it's full; in-flight queries keep
their data alive, so eviction is always safe. The hot working set stays close to compute
for speed while the long tail stays in cheap storage, and you don't have to decide up front
which is which.
